## Evidence hierarchy

When two sources conflict, use this order unless a newer explicit decision supersedes
it:

1. Current executable code and the actual instantiated checkpoint configuration.
2. Actual arrays/manifests generated by that code.
3. Tests that match the current API and format.
4. Official paper/repository/checkpoint metadata.
5. Local explanatory Markdown and old handoffs.
6. Proposed designs in this context pack.

This ordering matters because the local touch README and tests describe an older
format and older sampler behavior. They are valuable historical intent, but they are
not the current data contract.

## Checkpoints and exact configuration

The fork itself still does not contain the checkpoint payload because `checkpoints/`
is ignored. The follow-up audit nevertheless retrieved and inspected the official
VAE artifacts and released generator YAML outside the fork.

The official sparse-structure encoder contract is now confirmed:

- wrapper: `SparseStructureEncoderTdfyWrapper`;
- input channels: `1`;
- latent channels: `8`;
- channels: `[32, 128, 512]`;
- residual blocks per level: `2`;
- middle residual blocks: `2`;
- dense input: `[B,1,64,64,64]`;
- posterior mean/log-variance: `[B,8,16,16,16]`.

The inspected Stage 1 generator YAML confirms shape `[B,4096,8]`, model width 1024,
24 blocks, 16 heads, q/k RMS normalization, and layout fields
`6drotation_normalized`, `translation`, `scale`, and `translation_scale`. It also
selects DINOv2 ViT-L/14 registers at input size 518 and a pointmap patch embedder at
input size 256 with patch size 8.

Still open for the training integration are runtime condition-token counts, exact
pipeline-selected preprocessing/pose behavior, checkpoint parameter probes, and the
training orchestration that was not released. These no longer block deterministic
shape-target generation.

## Official architecture evidence

The official SAM 3D Objects paper (arXiv `2511.16624`, v2 inspected) states:

- Stage 1 models geometry and layout jointly as
  `p(O, R, t, s | I, M)`.
- Occupancy `O` is represented at `64^3` and encoded to an 8-channel `16^3` latent:
  4096 shape tokens.
- Rotation, translation, and scale each use one token.
- The model width is 1024 in the reported architecture.
- Shape uses its own transformer stream; layout modalities share a transformer and
  can use shape information through multimodal self-attention.
- Training uses rectified flow with
  `x_t = t x_1 + (1 - t) x_0`, target velocity `x_1 - x_0`, and multimodal MSE.
- Reported modality loss weights are shape `1`, rotation `0.1`, translation `1`, and
  scale `0.1`; AdamW is reported with no weight decay.

These paper facts constrain intent but do not replace the released checkpoint config.
The paper's full-model training scale and schedule are not automatically appropriate
for a small touch adapter.

## Training infrastructure audit

Searches across `sam3d_objects` and notebooks found no task training stack:

- no concrete `torch.utils.data.Dataset` or `DataLoader` for Stage 1 training;
- no `training_step`, `configure_optimizers`, Lightning `Trainer`, or training CLI;
- no released Stage 1 target cache builder;
- no touch modules or touch-aware configuration;
- no optimizer/checkpoint code for model training.

Occurrences of `torch.optim` are limited to layout/texture post-optimization during
inference. They are not reusable evidence of the original Stage 1 trainer.

The release does provide the lower-level pieces needed to build a trainer:

- preprocessing and pose conversion utilities;
- the SS VAE encoder/decoder;
- `FlowMatching.loss`;
- condition fuser/dropout machinery;
- Stage 1 model definitions and checkpoint loading.

## Known documentation/test drift

`TOUCH_SAMPLING.md` and `test_sample_touch.py` describe format v2 behavior such as
vertex centers, hidden-only neighborhood points, `center_vertex_ids`, and older
render orchestration. Current `sample_touch.py` and actual files use format v4,
master-sample centers, optional all-point neighborhoods, `center_point_ids`,
`center_face_ids`, `center_barycentric`, `point_visibility`, and fast-marching
distances.

Examples of stale test expectations include:

- `format_version == 2` while the sample is v4;
- `center_vertex_ids` while current output uses `center_point_ids`;
- monkeypatching `subprocess.run` while current rendering uses persistent
  `subprocess.Popen` workers/executors;
- assumptions that all neighborhood points are hidden while current default mode is
  `all`.

The historical statement that 13 tests passed should not be treated as verification
of the current code. The tests were inspected, not run, during this documentation
task because they are visibly out of sync and running them would not validate the
present format.

## Reproducibility boundary

Locally reproducible without gated assets:

- parse and audit manifests and the one sample object;
- load/validate all NumPy and image artifacts;
- inspect data-generation and model source;
- unit-test isolated touch/data logic if dependencies are present;
- develop config-agnostic modules and pure tests.

Not locally reproducible from the audited snapshot:

- regenerate the example object (source OBJ/materials absent);
- create a real SS latent target (source mesh and encoder weights absent);
- instantiate the released Stage 1 model exactly (YAML/weights absent);
- measure real token widths/counts or attention parameter names from the checkpoint;
- perform a faithful touch-conditioned train/inference smoke test.

Those operations belong on the cluster/full dataset environment after gated checkpoint
access is established.
